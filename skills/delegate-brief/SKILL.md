# 派发简报

主代理自己做是默认，派子代理是例外。

## 派发门

派之前答三问，三个都不是就自己做。简报第一行写命中的是哪一条。

| 理由 | 判据 |
| --- | --- |
| 主上下文已膨胀退化 | 能指出退化的迹象：重复读同一文件、忘了早先的决定、回答变短变糊 |
| 需要新鲜且用完即弃的上下文，并且能并行 | 这份工作读的东西主上下文不需要，做完就能扔；或者几份互不相交的工作能同时跑 |
| 主代理在这类工作上选不对工具或被冲突指令卡住 | 同一类错误已经出现过两次 |

要新设一种子代理，先试试把它的做法写成技能让主代理自己按需加载，试过不行再设。角色数量只减不增。

## 四样东西缺一不可

1. 清晰的目标与指令。
2. 行动边界：写范围、禁令、停点、完成即止。能用宿主的权限和门禁实现的硬限制就不靠提示词。
3. 必须遵守的规格。
4. 参考用的信息包。

缺任何一样，子代理的行动就不可控、难预测。

## 交回

要原始结果加指针：改了哪些文件、测试输出、发现的清单与位置。不要只给摘要。主代理自己读产物再下结论，不把子代理的结论直接当事实。验收只认 spec 的标准，不认子代理对自己工作的报告。

## 派评审者时

评审者只做确定性核对：给它 spec、不变式、改动与读数，让它逐条核承诺有没有做到。不派「找问题」「挑战设计」的对抗性评审，那种评审的上下文和实施方不对齐，带来过度设计和鸡毛蒜皮。

## 撤掉或合并一种子代理

带与不带各跑一遍同样的切片，比哪些验收项翻转了，不比总分。跑两次以上再下结论。一次只改一处。

## 外部技能

派发的流程调用 Skill 工具加载 `pstack:poteto-mode` 中的子代理章节。
