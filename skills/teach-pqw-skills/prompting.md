# 提示怎么写

流的步骤由技能提供，提示只说意图和完成判据。几句话比一份规格好。

## 开场提示写进去的

- 目标：要给用户什么能力，系统前后有什么差别。
- 完成判据：能过或不过的检查。「做好一点」和一个时长不是判据。
- 已知事实：相关的文档、现有领域、先例、已经定了的决定。省代理一次搜索。
- 真实约束：「不动现有公开契约」「先只做设计不写代码」「落盘前给我看」，每条都会改变代理的做法。

## 不写的

- 怎么做。说要达到什么，把路留给代理。
- 技能和步骤的清单。手写的顺序会丢步或乱序，入口技能会把 13 个环节写进任务清单。只在要改某一处选择时点名一个技能。
- 原因的猜测，直到代理先复述了问题。先说的猜测会收窄搜索。

一条可用的开场：

```
我们要给系统新增「<领域名>」领域：<用户得到的能力>。做完的判据是 <可核对的检查>。相关的正式文档在 <位置>，已经定了 <决定>。按单会话研发流走，定义期我在场。
```

## 定义期里怎么说

- 代理复述目标后先纠偏，再往下走。
- 每一步只回答那一步的问题。代理追问不变式，就答不变式，不提前讲实现。
- 拍板就说「定了」；不定就说「这个待定，先往下走」，代理会把它记进单子，交接点前必须清掉。
- 形式化建议来了，只答投不投、投哪一块。

## 离开前说的

- 说「我走了」或「交接点过了就自主推进」，代理不再来问。
- 把完成写成每个切片都能跑的检查，写进 spec 的验收标准。
- 预先回答代理会停下来问的事：「提交不用问我」「汇报件放临时目录就行」。
- 给一个出口：「两轮收口不收敛就停下写清楚原因」。

## 一行纠偏

- 回到目标：「我说的是先定边界，没让你写代码。」
- 点名环节：「回到第 2 步，先分领域。」
- 点名规则：「确定性验收，不做对抗性评审。」「派发门三个理由是哪一个。」「不过度设计。」
- 换题：「新任务」，代理重新判断够不够格。
