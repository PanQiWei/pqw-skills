# 心智模型与哲学

给人讲的版本。每条先说它在解决什么，再说做法，最后说少了会怎样。

## 这条流在解决什么

长程的软件开发里，代理一直面对同一组难题：设计会偏，代码会糙，边界会漏，上下文会腐化，人盯不住每一步。这条流是一条控制回路：动手前把不确定性尽量消掉，然后把执行放手给代理，再用固定节拍从顶层回看。它要做到五件事：

1. 设计正确且合理。需求先于不变式，不变式先于领域，领域先于架构，架构先于实施。
2. 代码不只正确，还要优雅、整洁、有品位，性能满足需求。
3. 控边界，控熵。领域边界与跨域协作先定后动；把不确定性从实施时搬到动手前。
4. 分阶段、增量、独立可验证、敏捷地交付。
5. 人的注意力到了某个阶段就抽离，之后只停留在高层。

五件事是目标，流和技能是手段。判断任何一步该不该做，拿这五件事当尺子。

## 为什么分两期一点

定义期由人主导。六步从需求走到正式落盘，每步回答一个问题、产出一样东西，产出是下一步的输入。顺序不能跳，因为后一步的判断建立在前一步的结论上：不知道不变式就分不出哪个领域是重点，不知道领域边界就没法判断该复用什么。

交接点是物理条件，不是感觉：长期维护的知识已经写进唯一源并过了评审。用一个没有本次上下文的会话问四个问题，答得出才算过。这一点的意义是，之后的代理不再依赖人的记忆和对话历史，依赖的是文档。

交付期由代理自主。spec 定边界，plan 切成有序切片，每个切片以 TDD 推进、独立收口。人在这一期只看汇报件和待决事项。

少了定义期，代理会在实施中边做边猜边界，返工发生在最贵的时候。少了交接点，人走开之后代理手里只有对话记忆，一次压缩就丢。

## 人的注意力为什么要抽离

人盯逐行实现，既盯不过来，也会把自己的注意力花在最不值钱的地方。这条流把人的注意力定价：定义期花在边界与不变式上，交接点花在确认知识已落地上，交付期只花在架构、产品和交互体验上。汇报件因此用架构图、UML 和快速 demo 讲「实现在架构层面长什么样、和之前比有什么区别」，不讲代码。汇报件用完即弃，放系统临时目录，不进仓库，因为它是给这一刻的人看的，不是长期知识。

## 为什么验收是确定性的

验收和评审用确定性的上下文：测试、形式化证明、结构读数、差分变异、对照 spec 的验收标准逐条核。评审者拿到的是 spec、不变式、改动和读数，核的是「承诺的有没有做到、守的有没有守住」，不是「我会不会这样写」。

不做对抗性评审。对抗性评审的上下文常常和实施方不对齐，结果是过度设计、过度优化，和陷进鸡毛蒜皮的细节。同一条品味也约束主代理自己：自主推进时不陷进细节，写代码按入口的[写代码的四条](../single-session-dev-flow/SKILL.md#写代码的四条)：先做对，再做好一轮，不提前优化，找本质解。

靠测试守不住的性质，交给形式化：偏函数定义并全化、数理建模、定理与证明，实施时转成契约测试。分工是证真交给证明，证伪交给测试。触发由代理建议、人确认，因为形式化有成本，投不投是人的判断。

## 为什么默认不派子代理

主代理自己做是默认。一个主循环加按需加载的技能，比多代理更快、上下文更对齐。派子代理只有三种理由：主上下文已经膨胀退化；工作需要新鲜且用完即弃的上下文并且可以并行；主代理在这类工作上选不对工具或被冲突指令卡住。派的时候四样东西给齐：目标与指令、行动边界、规格、信息包。交回要原始结果，不要摘要，因为摘要会把失败写成成功。

计划者就是执行者：plan 由主代理写，结果回来就修订。不交给别人规划再交给别人执行，中间那次交接丢的正是判断的依据。

## 为什么要定时回看

一堂课法则：自主交付期间按一程预算定的间隔从顶层回看，间隔是总预算的六分之一，最短 10 分钟、最长 45 分钟，子代理每运行 30 分钟查一次健康度。靠主代理自觉回看不可靠，让它自己判自己更不可靠，因为腐化的上下文觉得自己没问题。所以派一个独立的、便宜档的哨兵子代理常驻后台：它持有同一份 spec 与 plan，自己计时醒来，拿脚本取工作树事实，判有没有偏离、兜圈、腐化、子代理是否健康，写一条记录并给主代理发十行以内的消息；主代理在停顿点处置，不被打断。哨兵两次之间阻塞等待，不烧 token。一程和每个切片都带时间预算，到了预算就回看，不继续跑，因为跑偏的代理越跑越远。

## 三级与圈外

一程只对自己的承诺负责。定义期把受影响的领域分成重点、次要、连带三级，分法看的是它与本程改动的关系：为兑现承诺而改的是重点，因为本程的改动而必须跟着改、跟着验的是次要与连带。spec 的「责任分级」把三级写成路径，交付期就有了可核对的边界；三级之外都是圈外。长程交付里总会碰到圈外的东西：别的模块的旧缺陷、产品上设计了还没实现的机制、无关的失败用例。修它要别人的设计上下文，会越过原拥有者；为它停下要人的注意力，那是最贵的。所以圈外的东西默认记一行就继续，只有它挡住本程某条验收标准时才处理，处理也先找圈内的绕法。例如本程改了「依赖不可用时等待」这条承诺，循环的转移表要为它加一条边，转移表就是连带，哪怕 spec 没列它；同一张表里一条与本程无关的旧缺陷是圈外，记一行，不修。判法与处置表在入口技能的[圈外的问题](../single-session-dev-flow/SKILL.md#圈外的问题)一节。少了这一条，代理会在局部越挖越深，或者为不相干的事停下来问人。

## 为什么不走缩水版

这条流只为大改动设计：新增领域、跨多领域的功能纵线、子系统重构、较大规模改造。判据是影响范围。小修、原型、小规模增量接口不走，直接按各自的技能做。不走缩水版，因为流的价值在完整：跳过的那一步正是后面出问题时没人核过的那一步。缩水的入口要另起技能，不改总入口。

## AI 主导研发交付的心智

这一节给接入这条流的项目用：设计自己的合入检查、分支与人审规则时，拿它当尺子。它不讲怎样写代码，写代码按入口的[写代码的四条](../single-session-dev-flow/SKILL.md#写代码的四条)。

出处是两篇一手文章：Anthropic 的 [Redesigning source control at Anthropic](https://www.anthropic.com/engineering/redesigning-source-control)（2026-10-13），讲代理写代码之后版本控制在规模上撑不住的地方；[How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)（2026-10-15），讲代理写代码之后人该审什么、合入检查怎样设。

主线是一句话：人主导时的研发流程防的是人，AI 主导时的研发流程要防代理。代码托管平台和多数团队流程是为很多人并行协作设计的，防的是人的失败：忘了跑测试，不知道别人在改什么，贡献者不可信，口头承诺没人记，知识只在少数人脑子里。对策是锁、认领、看板、状态档位、交接报告、多人评审、多层分支。代理的失败不一样。只要流程要求，它不会忘记跑测试，不会累，也不缺上下文里写明的知识。它会偏离意图、过度设计、为了变绿去改测试、违反没写下来的系统约束、声称完成却没有证据，产出量还会淹没人的注意力。把防人的物件原样套在代理身上，代理的 token 大量花在簿记上，真正防代理的检查只占一小部分。下面十条由此展开。

1. **人的注意力是最贵的资源。** 流程要省的是人的时间，不只是代理的 token。衡量一个流程，看每个改动花了多少人时、多少 token；护栏是主干的回退与集成事故不增加。省下的人时换来了回退，就是没省，只是挪了地方。
2. **按失败模式配检查，不按流程形态配。** 检查多了不等于稳，每道检查都要花 token 和等待。每道合入检查都要答得出：它防哪一种失败，换成别的检查会不会更便宜。答不出的删。这与本流的切片收口不冲突：收口只用确定性检查，这一条讲的是项目合入前该留哪几道。
3. **防代理的检查留，防人的协调物件删。** 把防人的物件套在代理身上，簿记会挤掉真正的检查。防代理的有四类：没有证据的完成，由流程重跑确定性检查，不信自述；改测试迁就实现，用验收锁；违反系统约束，用依赖方向检查与公开契约快照；偏离意图，由人在定义期定意图，在合并时读证据与意图。一个任务一个会话之后，认领、看板档位、多人并行改同一处的协调、交接报告格式这类物件没有对象了。
4. **风险由改动决定，风险决定人审多少。** 作者自评风险不可靠，代理更是如此。级别在定义期写进交接信息包，合并时再按改动碰到的路径复核，取高的一个。持续集成与检查的定义、验收测试、公开契约、工具链这些高风险路径永远要人审。代理的批准不算人的批准，一次批准只覆盖一个具体提交。
5. **人做五件事，其余交给机器。** 人的判断稀缺，不该花在机器能抓的常规错误上。人做五件事：定方向与范围，审高风险代码与会被别人照抄的架构，读证据，对结果负责，对代理说不。人不逐行读常规改动，不当 lint。
6. **审查前移且连续，评审轮数封顶。** 审查越晚，返工越贵；审改不封顶，会一夜几十轮地兜圈。收口在每个切片里做完，用确定性上下文，做法归 `slice-closeout`。两轮不收敛就先质疑判定或缩窄承诺，再按[写代码的四条](../single-session-dev-flow/SKILL.md#写代码的四条)第四条找本质解，不继续审改。
7. **合入前只拦确定性检查，并在合并结果上跑。** 两个各自通过的改动可能合出一个坏的目标分支。合入前只放 lint、类型、测试、构建这类结果确定的检查，红了就挡；它们跑在「改动合入目标分支最新提交」的结果上，不跑在改动自己的分支头上。
8. **合入后靠回退兜底，不靠堆合入前的检查。** 合入前的检查堆得越多，每个改动越慢，漏网的还是会漏。新行为先藏在开关后面，集成分支先于稳定分支接收改动；集成分支红了，先回退那次合并再修。
9. **少全局状态，少分支。** 代理数量大、永远在线，每一份全局状态都会变成争用与簿记。长期分支只留主干、发布与必要的一层集成，例如一条集成分支、一个主干、一个稳定分支；任务状态用平台原生的开与关加上改动的关联，不维护多档看板。
10. **教训进结构，不进记忆。** 记在对话或个人记忆里的教训，下一个会话看不到。漏检之后问代理面前缺了什么，把修正落到项目入口文档、技能或检查脚本；同一类问题第二次出现就写成检查。这条与 `one-lesson-rule` 的定时回看同源：切片本质上都简单，做久了是没找到本质解，就回到建模。
