# 诤友：值不值得做

接需求时有两个互不相干的问题。一个是值不值得做：有没有人真要，今天怎么应付，最小做到哪。另一个是怎么做清楚：沿设计的每个决定点问到两边理解一致，归 `mattpocock-skills:grilling`。前一个排在复述目标之后、追问之前。次序不能反：先问清怎么做，等于默认了它值得做。

**第 0 步：先查，不问。** 事实归代理去查，决定才归人。查三件：是不是已经有了，代码和文档里有没有现成的实现或一部分；以前是不是拒绝或推迟过，查不做与推迟的记录；有没有既有的决定，相关的工单与正式文档里已经定下的事。查到已经有了或以前拒绝过，用固定格式告诉人，不往下问。

**第 1 步：按需求的种类选问题。** 已经答过的跳过。

| 需求的种类 | 问哪几问 |
| --- | --- |
| 给用户的新能力 | 需求证据、现状、具体的人、最窄切口 |
| 内部工具、流程 | 现状、最窄切口 |
| 重构、优化、基础设施 | 现状（带测量或事实）、最窄切口 |
| 修复 | 不问 |

1. **需求证据。** 现在有谁真的在等它？有没有比「感兴趣」更硬的证据：有人被卡住了，有人在用笨办法顶着，有人明说没有它不行。
2. **现状。** 没有它，今天是怎么应付的？这个办法的代价是什么？
3. **具体的人。** 最需要它的是哪一个具体的人或角色，在什么时刻用？
4. **最窄切口。** 最小做到哪一步，这个人这周就用得上，你也看得出它有没有用？

**第 2 步：一轮问齐。** 每问后面写代理查到的或猜的答案，标明「查到」或「猜」，措辞让人答「对」就算接受。例：「现状：现在是手工改配置再重启，每次约十分钟（查到）。对吗？」不知道的直说不知道，不编。该人答的，代理不替人答。

**第 3 步：前提逐条确认。** 列出这个需求成立要靠的前提，一条一句，人逐条答同意或不同意。固定三条：这是不是对的问题，换个提法会不会简单得多；什么都不做会怎样；现有的东西已经解决了多少。

**第 4 步：表态。** 给出四种结论之一，带依据，并说什么证据会让自己改主意。不说附和的话。

| 结论 | 什么时候 |
| --- | --- |
| 照做 | 该问的都答得出，前提都同意 |
| 缩小到最窄切口 | 需求是真的，但要的比验证它所需的多。最窄切口就是第一程，其余进[分程建议](run-size.md) |
| 先取证再做 | 需求证据或现状答不出。建议一种最便宜的取证办法：去问那个人，知道答案的是第三个人时按已安装路径直接读 `mattpocock-skills:to-questionnaire` 的正文生成一份问卷，并在报告里写明读取方式；看一次现在怎么用；做一个用完就扔的原型，加载技能 `mattpocock-skills:prototype`。人可以不取证 |
| 建议不做 | 没有人在等，没有现状的代价，或者已经有了 |

再对着三种有名字的坏需求核一遍：找问题的方案，只有机制，没有谁得到什么；想象中的用户，说不出具体的人；把感兴趣当成需求，没有人被卡住。

整轮答完，只对决定结论的那一个回答追问一次。第一个回答往往是说顺了的版本，追一次能问到实情；追两次就是纠缠。

**第 5 步：人定。** 人怎么定就怎么做，之后不再争。结果写进需求单的「值不值得做」一节。人定了不做或推迟的，按概念记一条不做与推迟的记录，写理由，下次有人提相似的需求能对上。记在哪由项目接入点的槽位定，没填就写在需求单里。

不够格走这条流的小活不走这几步。只在一种情况下开口：证据排除了人要的改动，或者看得出它解决不了人说的那个问题。
