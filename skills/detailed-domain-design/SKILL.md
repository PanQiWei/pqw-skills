# 细化领域设计

三件事有机结合：DDD 领域建模定概念与边界，SOLID 的关系模型定对象怎样协作，仓储设计定数据怎样进出。它们不是三份文档，是同一份设计的三个视角。

## 领域建模

从领域影响分级表的重点领域开始，次要领域只建到履约必需的部分，连带领域只定接口。

- 统一语言：每个概念一个名字，和需求与不变式单里的用法一致。改名要回去改单子。
- 聚合与边界：谁拥有状态，谁发起变化，变化的原子范围是什么。跨聚合的一致性靠事件或流程，不靠跨聚合事务。
- 领域不认识调用方：领域只按外部需求的本质提供服务，不知道调用它的是哪种会话、运行或代理。外部的业务事实由外部凭身份关联。
- 外域概念只建到履约必需：消费的是契约、投影还是引用，在 spec 的跨域五问里定。

方法调用 Skill 工具加载 `mattpocock-skills:domain-modeling`。

## 关系模型

先写类型、签名与模块边界，再写实现。调用 Skill 工具加载 `pstack:architect`。设计时核的是：

- 深模块：接口小，功能深。调用 Skill 工具加载 `mattpocock-skills:codebase-design`。
- 非法状态不可表示，语义基元有类型，外部数据在边界解析。调用 Skill 工具加载 `pstack:principle-type-system-discipline`。
- 校验与错误处理集中在系统边界，内部不重复防御。调用 Skill 工具加载 `pstack:principle-boundary-discipline`。
- SOLID 按真实的变化轴拆，不为拆而拆。一个类只有一个变化的理由，扩展靠新实现不靠改旧代码，依赖抽象且抽象由使用方拥有。

## 仓储设计

有存储需求时单独做，不留给实施期顺手写。没有专门设计时，当前的代理写存储和 I/O 很容易写出性能差的代码。固定回答四问：

| 问 | 要定的 |
| --- | --- |
| 写入路径 | 每次写入的形状、频率、大小；批量还是逐条；是否幂等；失败后重试会不会重复 |
| 查询路径 | 每种查询按什么键、返回多大、多频繁；需要哪些索引；有没有全表扫描 |
| I/O 形态 | 同步还是异步；流式还是整块；并发写的隔离；事务边界 |
| 容量假设 | 一年后的数据量；超过假设时哪条路径先坏 |

仓储接口归领域，实现归基础设施。接口只暴露领域需要的操作，不暴露存储细节。性能目标达到形式化守护的触发条件时，先走 `formal-guard`。

## 产出

填[细化设计清单](design-template.md)。清单填完的判据：每个重点领域有聚合与边界；每个公开接口有类型与签名；有存储的领域四问都有答案；每条不变式能指到守它的对象或边界。
