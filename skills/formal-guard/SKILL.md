# 形式化守护

## 触发条件

出现下面任何一项，先做形式化再实施：

- 较高的性能要求。
- 数据生命周期、状态机、状态转移。
- 并发、多线程、协程、池化。
- 跨领域协调边界上要守住的性质。

## 谁判断

代理按上面四类触发条件给出建议，说明命中了哪一类、要形式化的是什么性质、大致成本。人确认后才投入。形式化成本不低，判错方向会浪费一程。

## 核心命题

测试只能发现缺陷，不能承诺没有缺陷。数理建模和证明可以在相当程度上承诺照着实现没有这一类缺陷。所以证真交给证明，证伪交给测试，两者不互相替代。

## 产出

- 偏函数定义与全化。
- 数理模型、定理与证明。
- 实施时要转成契约测试的清单。

## 外部技能

- 选工具、生成项目内的验证技能并先证明检查能失败，调用 Skill 工具加载 `pstack:create-formal-verification-skill`。
- TLA+ 模型的结果读成状态图，调用 Skill 工具加载 `pstack:statechart`。
- 代码变化后把模型、性质同步回代码，调用 Skill 工具加载 `pstack:maintain-formal-verification-skill`。
