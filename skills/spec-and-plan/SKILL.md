# spec 与 plan

交接点过了，主代理写两份开工文档，之后整程按它们推进。spec 回答做什么、做到什么算完；plan 回答按什么顺序做、每片怎么验。

## 顺序

先 spec 后 plan，不并行。plan 是 spec 的分解，spec 没定边界就切片，切出来的片会互相打架。

## 写 spec

按 Matt 的 `to-spec` 做：综合会话里已经讨论和定义期已经落盘的内容，不重新访谈；先找测试接缝，越高越好、越少越好。填 [spec 模板](spec-template.md)。本模板比 Matt 的骨架多五节，每节对应定义期的一个产出：

| 节 | 来自定义期的 | 为什么要有 |
| --- | --- | --- |
| 依据与已定事项 | 正式落盘的文档与修订 | 让每条实施决定能追到已接受的承诺 |
| 不变式对照 | 需求与不变式单 | 每条不变式写由什么守、怎么验，不留口头承诺 |
| 跨域概念的五问 | 领域影响分级表 | 新增或改变跨域概念时必填，没有时写不适用 |
| 失败语义 | 细化设计清单 | 正常、失败、未知、取消与清理、外部效果五行，各写行为、责任人、验证 |
| 责任分级 | 领域影响分级表 | 让交付期有可核对的边界 |

改了既有承诺时，在不变式对照下面写「- 旧字面：`<旧原因码>` `<旧状态名>`」，再跑 [`scripts/consumers.mjs --spec <spec.md>`](scripts/consumers.mjs)。断言旧承诺的测试与文档也是消费者：源码的调用方能按引用找到，它们只能按字面找，而且常在别的成员、在慢的那层测试里。脚本按字面在 Git 跟踪的文件里搜，标出不在责任分级里的命中；范围外的要么补进责任分级，要么确认它不受这次改动影响。交付期扩了范围后再跑一次。

待决事项先筛三层：过度设计删掉；自己能定的写进已定事项；只有产品规则、范围变化、新的破坏性契约改动、须人本人做的动作才算缺口。

## 写 plan

按 Matt 的 `to-tickets` 做：切成端到端的薄切片，每片能单独验证、能在一个新上下文里完成，前置的预重构先做，每片写明被谁阻塞。填 [plan 模板](plan-template.md)。和 Matt 原版的差别：

- 写成员、文件与验收命令，因为主代理在当前仓库执行，不是发给别人的工单。
- 进度总览格式固定，哨兵与汇报件直接读它。
- 每个切片下面留开工包四节：上下文增量、技术细节设计与验证、细化的推进方案、里程碑待办清单。开工包在切片开工前填，做法归 `context-pack`。
- 每个切片带收口清单，做法归 `slice-closeout`。
- 末尾是一程交付声明，含清理已做。
- 多两处给人读的叙述：开头一节「一程目标与前后差别」，每片一项「交付这片的意义」。
- 多一节圈外发现：碰到圈外的问题记一行，进度总览带条数，收口时一次交给人。判法与处置按入口[圈外的问题](../single-session-dev-flow/SKILL.md#圈外的问题)。

### 给人读的两处怎么写

读者是把注意力移开一两个小时后回来的人，他要靠这两处对齐上下文，不翻源码。所以：用完整的句子，不用缩略语和内部短语；产品与技术两层各至少一段；术语第一次出现时用一句话解释它是什么；先说现状与为什么不顺，再说做完之后怎样，最后说他怎么看出来变了。「交付这片的意义」分「对用户」与「对系统」两句，前者说他能看到什么或少做什么，后者说这片改了哪个环节、为什么它先做。写完自己读一遍：一个不了解这个系统的人能不能读懂这程为什么做。

### 文档维护表与局部编辑

plan 里的「文档维护表」列出一程里每份给人看的文档：给谁看、什么时候更新、只动哪一节、怎么判断过期、最近更新。开工时照模板填上路径，之后每次更新某份文档就改它那一行的「最近更新」。更新一律局部编辑：找到对应的节或行再改，不整份重写，不改节标题与表头，新增内容进模板规定的位置。节标题、表头、进度行与处置行的格式是哨兵脚本与汇报件脚本读的契约。局部编辑用宿主的编辑工具做替换；自己写脚本改文件时先把内容读进来再写回，不要先以写模式打开再读，那样文件先被清空，读到的就是空。

[`scripts/check-plan.mjs`](scripts/check-plan.mjs) 按模板核 plan 与 spec 的骨架：必需的节在且顺序对、进度行与处置行格式对、切片表与维护表的表头齐、每片有意义段与收口清单、spec 的责任分级有带反引号路径的重点行。它在三处跑：切片收口的最后一步、哨兵每轮取事实时、汇报件生成之前。红了不算收口。交付会话从[交接信息包](../single-session-dev-flow/handoff-pack-template.md)开工时，先用 `--handoff <包>` 单独核包的结构，含边界里的责任分级表。

Matt 的 `to-tickets` 要求人批准切分。走这条流时人已经在交接点移开注意力，所以切分由主代理自己定，写进 plan 即可；人要看随时能看。

## 读 Matt 正文的方式

`to-spec` 与 `to-tickets` 声明了 `disable-model-invocation: true`，宿主不让模型自动加载它们。按已安装路径直接读它们的 `SKILL.md`，并在报告里写明读取方式；路径在宿主的技能安装目录下，例如插件缓存目录里的 `mattpocock-skills/<版本>/skills/engineering/<名字>/SKILL.md`。找不到时报告缺口，用本技能的两份模板继续，不停。

## 放哪

项目 tmp 下本程的目录，例如 `tmp/<一程名>/spec.md` 与 `plan.md`。它们是过程材料：正式形状与长期契约归项目的正式文档，一程交付后按 `cleanup` 处理。
