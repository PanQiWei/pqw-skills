# 结构读数与差分变异的模型

与语言无关的定义。自带的工具按这份模型实现，语言适配器只负责把源码变成这里的对象。定义取自 Robert C. Martin 的 crapper 与 mutator（0BSD），计分单元的划分取 omne 的做法。

## 对象

| 对象 | 字段 | 含义 |
| --- | --- | --- |
| 单元 Unit | path、namespace、name、startLine、endLine、startByte、endByte | 一个计分单元：有名字、有函数体的函数或方法。限定名 `namespace.name`。单元之间可以嵌套，行范围内扣掉更内层单元的行才是它自己的行 |
| 判定 Decision | kind | 语法树上使控制流分叉的节点。集合 D 由语言适配器声明 |
| 行命中 LineHits | file → line → (covered, total) | 覆盖率报告里每行的命中。lcov 的 DA 记录是 (hit > 0 ? 1 : 0, 1)，BRDA 记录按行聚合成分支的 (covered, total) |
| 位点 Site | file、unit、line、anchorLine、start、end、original、mutant、category | 一处可替换的文本。anchorLine 是所在语句的起始行，多行语句只有这一行有覆盖记录 |
| 裁定 Verdict | killed(reason?)、survived、uncovered、notRun(reason) | 一个位点跑完的结果。killed 的 reason 可为 timeout；notRun 的 reason 取 noTests、crashed、budget、baselineFailed |

## 定义

- **圈复杂度** `CC(u) = 1 + |{d ∈ D : d 在 u 自己的行内}|`。更内层单元里的判定不算在外层头上。
- **认知复杂度** `CogC(u)` 按 SonarSource 白皮书三条：每个分叉结构 +1；嵌套在另一个分叉结构里的结构再加嵌套深度；同一表达式里逻辑运算符每换一种 +1。`else if` 与链尾的 `else` 各 +1 且不加嵌套，所以 `if … else if … else` 记 3。适配器声明哪些节点是分叉结构、哪些增加嵌套。
- **带位** 每个单元按两条线归到 ok、warn、alert 三档之一；圈复杂度的线总是看，CRAP 的线只在算得出时看，都没过线而 CRAP 算不出的记「无覆盖」。缺省线：圈复杂度 warn 10、alert 12，CRAP alert 30，严格大于才过线（CC 11 是 warn，13 是 alert；CRAP 31 是 alert，30 是 ok）。线可由调用方覆盖，读数 JSON 的 `thresholds` 记实际用的线。带位只是报告的标记，不是接受判据；过线的单元怎样交代归 `slice-closeout` 正文。
- **覆盖率** `Cov(u) ∈ [0,1] ∪ {null}`，三态：有值；未提供（没给覆盖报告）；无数据（报告里没有这个文件，或 u 自己的行上没有任何记录）。有记录时：有分支记录就取分支的 `covered / total`，否则取行记录的 `covered / total`。后两态 Cov 为 null，并带原因；不写成 0，因为 0 是「跑了测试一行没碰到」，与「不知道」是两回事。报告里找文件照 crapper：全等优先，否则整段路径后缀匹配（任一方向）恰一个才取，多个候选记「多个文件匹配」不猜。报告的可信度有三条警告，写在抬头与 JSON 的 `warnings`：报告早于被度量的改动文件（行号可能错位）；改动函数全部零命中（可能没跑到或报告过旧）；多个文件匹配同一路径。
- **CRAP** `CRAP(u) = CC² × (1 − Cov)³ + CC`，Cov 为 null 时 CRAP 为 null，报告 CRAP 列写「无覆盖」，覆盖率列分别写「未提供」或「无数据」。
- **基线比** 每个改动函数带基线版本同限定名单元的圈复杂度与认知复杂度（基线没有记 null）与趋势：新出现 new；圈复杂度涨 up、降 down；相等再看认知复杂度；都相等 same。变差 = 带位过线（warn 或 alert）且趋势是 new 或 up。报告全部列出，变差的标出并排前面；收口只逐条交代变差的，其余只列不解释，不替历史交代。CRAP 不比，因为基线的覆盖率拿不到。
- **不度量的文件** 非源码、声明文件、测试文件不进改动函数表，列进「未覆盖的改动文件」带原因。测试文件的匿名用例回调全并进 `<module>`，覆盖报告又通常不含它，读数没有意义。
- **单元摘要** `Digest(u) = sha256(u 自己的各行去尾部空白后以换行拼接)`。同名单元按行号顺序把各自摘要拼起来再取一次。摘要相同就是函数文本没变，挪位置、上方加行都不算变。
- **改动单元** 基线 ref 到工作树的 diff 碰到的行所在的单元。只认 Git ref，不认任务绑定。
- **纯删除** 只删不加的改动在新一侧没有行，记删除点前后两行（删除点前一行与后一行，文件头删除记第 1、2 行），所以删掉函数里一行也算改了这个函数。
- **基线** 显式给的 ref 要是 HEAD 的祖先；基线分支前进过时改用它与 HEAD 的合并点，抬头写明，JSON 的 `baseGiven` 记给的提交。没给 ref 取与目标分支的合并点。读数只认 `--repo` 所在仓库，会把 git 指到别处的环境变量（`GIT_DIR` 等）一律剥掉。

## 变异

- **引擎** 两套，`--engine auto|stryker|builtin`，缺省 auto。项目用 vitest（根下有 `vitest.config.*` 或 `vite.config.*`，或 package.json 声明了 vitest）且找得到 Stryker 与它的 vitest runner 时用 Stryker 引擎，否则用内建引擎；抬头在基线说明之后写一行「引擎：Stryker <版本>（vitest）」或「引擎：内建（<原因>）」，JSON 顶层 `engine: { name, version, runner, reason }`。依赖按顺序找：项目根 `node_modules`、`--stryker-modules` 或环境变量 `PQW_STRYKER_MODULES` 指的目录、本技能 `scripts/node_modules`（`scripts/package.json` 钉版本，`npm ci --prefix <该目录>` 装）。显式 `--engine stryker` 而条件不满足退出 2 并写装法。两套引擎的分工：范围（改动行、点名文件、基线）、资源（份额算并行度）、读数（四类裁定、测量无效、未覆盖段、存活清单、抬头与 JSON 字段）由本工具算，两套一致；位点生成、写入变异体、跑测试、还原由引擎做。内建引擎逐位点写入工作树、每个位点跑一遍完整测试命令；Stryker 引擎把范围写成 `mutate` 条目（改动行所在单元自己的全部行 `路径:起-止`，与内建引擎打的行一致；不在任何单元里的改动行原样；点名文件整份写路径）与配置，在项目根起 Stryker，它在 `.stryker-tmp` 的副本里一次性插桩全部变异体、测试进程常驻、按逐条覆盖只跑碰到变异体的用例、几个进程并行；本工具读它的 JSON 报告映射回位点（单元按行找、原文按位置切、类别取变异器名去后缀小写），只收落在范围里的变异体，范围里没有变异体的段进「没有位点的改动段」。Stryker 引擎不改项目文件，只写 `.stryker-tmp` 与系统临时目录的工作目录（`pqw-mutation/<仓库根哈希>-stryker/`：配置、报告、日志、增量文件）；`.stryker-tmp` 跑完删，被 SIGINT、SIGHUP、SIGTERM 结束也删，只有被强杀时留下，没被项目忽略时抬头提醒。`baseline.seconds` 记初跑（未变异的一轮）用时，从 Stryker 日志取。初跑失败时退出 1，抬头写「测量无效（Stryker 初跑失败）」并在「基线不通过：」下给日志尾与完整日志路径。Stryker 引擎下 `--test` 可省略（vitest 由引擎起），`--budget` 不适用（引擎没有整轮预算，抬头写明），`--history` 不适用（增量由引擎负责，见下）；状态映射 Killed→killed、Timeout→killed(timeout)、Survived→survived、NoCoverage→uncovered、RuntimeError、CompileError、Ignored、Pending→notRun 带原因；映射表没有的状态记 notRun「未知状态 X」并使整次测量无效（原因写出状态名），不猜。
- **位点集合** 内建引擎由适配器按类别生成：relational（`<`↔`<=`、`>`↔`>=`）、equality（`==`↔`!=`、`===`↔`!==`）、logical（`&&`↔`||`、`??`→`||`）、arithmetic（`+`↔`-`、`*`↔`/`）、boolean（`true`↔`false`）、negation（删去一元 `!`）、optional（属性上的 `?.`→`.`，调用与下标上的 `?.` 删去）。只生成改动单元自己的行上的位点。
- **类型位置** 类型节点、类型别名与接口里的字面量与运算符不执行，改了测试也发现不了，不出位点；`type R = { ok: true }` 没有位点，`return { ok: true }` 有。
- **选择** 内建引擎有覆盖报告时只跑 line 或 anchorLine 被命中的位点，其余裁定 uncovered。有历史时，单元摘要未变且上次 killed 的位点不再跑，沿用上次裁定，抬头写「沿用 N」。Stryker 引擎的覆盖由它自己的逐条覆盖决定，不读 `--lcov`。
- **增量（Stryker 引擎）** 配置开 `incremental`，增量文件在工作目录；指纹（工具版本、「vitest@<版本> + <配置文件>」、测试文件摘要、Stryker 版本）记在同目录，与上次不同就 `force` 整轮重跑。沿用的个数从 Stryker 日志的增量摘要行取，抬头写「沿用 N」；首轮没有沿用时写「增量：已开，本轮没有沿用」。
- **点名文件** 调用方点名的文件全部有名单元都出位点，不论基线到工作树有没有改动，位点带 `pinned`；点名的文件不列未覆盖段，因为它不是按改动打的。用于判据与状态机所在的文件：改动在别处，但这些文件的测试是否守得住要一起看。
- **位点 id** `文件:单元:单元内偏移:类别:替换`，不含行号与文件内偏移：文件上方加几行不影响沿用，同一单元里同一处同一种替换就是同一个位点。
- **指纹** 结果 JSON 带 `fingerprint`：工具版本、测试命令、测试文件摘要（工作树里测试文件的路径与内容的哈希）。历史的指纹任一项不同，或历史没有指纹，整份不沿用，抬头写明原因；因为放宽或删掉一条断言后，上次的「杀死」就不再可信。
- **运行** 先在未变异的工作树上跑一次测试命令，不通过则整程 notRun(baselineFailed)。每个位点：读原文进内存，写入变异，跑测试命令，还原并逐字节核对。进程收到 SIGHUP、SIGINT、SIGTERM 时先还原全部已改文件再退出。
- **还原日志** 写入变异体之前先把 `{ root, path, original, mutated }` 落到系统临时目录（`pqw-mutation/<仓库根哈希>.json`），还原成功后删。进程被 SIGKILL 或断电时日志留下，下次启动先看日志：文件仍是变异体就写回原文并打印「上次运行留下的变异体已还原」；文件已是原文只删日志；文件是别的内容就是两次运行之间有人改过，不覆盖、保留日志、退出 1，由人核对后删日志。
- **改写保护** 写入前核文件仍等于原文，还原前核文件仍等于写入的变异体；不等就是测试期间有人改了文件，不覆盖，保留日志，打印「文件在变异期间被改动」退出 1。覆盖会丢掉人的改动，留下的变异体由日志在下次启动时还原。
- **裁定顺序** 超时记 killed(timeout)，摘要单列「其中超时 N」，因为超时可能是机器慢；测试命令被信号结束（或 shell 报告的退出码 128 以上）记 notRun(crashed)，不当杀死；非零退出记 killed；否则看「没跑测试」；都不是记 survived。
- **没跑测试** 测试命令输出匹配「没跑测试」模式时，同一位点按位置复跑一次，仍匹配记 notRun(noTests)。缺省模式带词界，「Tests 10 passed」不算。基线输出本身就命中模式时该模式判不出东西：抬头写明，裁定时不再用它，位点按通过处理。
- **存活清单** 只陈述事实：哪个位点、原文换成什么、测试仍过。怎么处置归读的人。
- **预算** 到时间预算后剩余位点记 notRun(budget)，退出码仍为 0，JSON 的 `budget.exceeded` 为 true。
- **分数** `killed / (killed + survived)`，没有已执行的位点时为 null。
- **测量无效** 基线不通过，或一个位点都没有执行（杀死加存活为 0：没有位点、全部位点无覆盖、没有执行任何位点），`valid` 为 false 并带原因，分数为 null，抬头写「测量无效（原因）」且不出四类计数。没有执行过的测量不能写成「杀死 0、存活 0」。只列时 `valid` 为 null。
- **未覆盖段** 改动了却没有位点的段单独列出，不进分数：改动行不在任何有名单元里（模块级；空行与只有注释的行不算），或改动的单元里没有可替换的位点。分数满不代表改动都被打过。

## 资源

变异工具是机器上的重型任务，它要自适应机器，也要给同机的别人留份额。与语言和测试运行器无关的部分如下，参数名与缺省见命令面的 `--help`。

- **容量** 启动时量：逻辑 CPU 数、可用内存（MB）、1 分钟负载。
- **份额** `1 / (同机另有的重型任务数 + 1)`。任务数由调用方声明，缺省 0。
- **并行度上限** `max(1, floor(CPU 数 × 份额))`；可用内存低于阈值时再减半（仍至少 1）。
- **并行度** 缺省等于上限；调用方显式给的并行度超过上限按上限，并在输出里写明。工具自己不并行，内建引擎下并行度只通过环境变量交给测试命令（`PQW_TEST_WORKERS`，另加常见运行器认的变量），避免两层并行相乘；Stryker 引擎下写进配置的 `concurrency`，启动时定下，运行中不调。
- **优先级** 测试子进程以较低优先级启动（能设的平台才设，设不了写明）。
- **运行中自适应** 只有内建引擎做。每个位点前采一次负载比（1 分钟负载 ÷ CPU 数）：超过上限就把并行度减半（至少 1）；回落到上限减去滞回量以下再翻倍（不超过计划值）；中间地带不动。并行度已是 1 还连续 3 次超限，记「机器繁忙」并继续跑。
- **自身开销** 记总耗时、测试命令耗时之和、两者之差占总耗时的比例。每个改动文件只解析一次，裁定位点只做字符串替换，不再解析。Stryker 引擎下只记一轮总耗时。
- **两种引擎的量法** 内建引擎一轮耗时约等于位点数乘整套测试一遍的时间，Stryker 引擎约等于初跑一遍加每个变异体只跑碰到它的用例，所以测试越慢、位点越多差距越大。同一基线同一范围的两组读数：一个三条用例的 vitest 小项目，改两行，内建 5 个位点 3.5 秒分数 40%，Stryker 20 个变异体 4.3 秒分数 75%（增量第二轮 2.6 秒、沿用 20），小项目上两种引擎耗时相当；本仓库自己（node:test，整套约 50 秒）一个切片改动 106 个位点，内建引擎 15 分钟预算只跑完 36 个。Stryker 的变异器更多，位点数与分数不能跨引擎比。
- **记录** 结果 JSON 的 `resources` 节记容量、任务数、份额、上限、实际并行度、显式值与是否被降、低内存阈值与是否减半、优先级、负载上限；跑过位点后再加 `adaptation`（当前并行度、采样数、降档与升档次数、最低并行度、是否繁忙）与 `timing`（总耗时、测试耗时、开销比）。表格末尾一行资源摘要，繁忙与开销也写在这一行。耗时数字要能解释：被挤占的慢不是工具慢。

## 适配器要给的

| 适配器 | 输出 |
| --- | --- |
| `units(source)` | 单元列表，含每个单元的 CC 与 CogC |
| `sites(source, units)` | 位点列表 |
| `decisions` | 集合 D 的说明，写在适配器文件头 |

TypeScript 适配器：判定集合为 if、三元、for、for-in、for-of、while、do、catch、case、default、`&&`、`||`、`??`、`?.`；有名字的内层函数、对象字面量方法与类字段箭头函数各自成单元，匿名回调并入外层。
