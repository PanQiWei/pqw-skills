# 单会话研发流

一程研发在一个会话里走完：人主导的定义期，代理自主的交付期，中间一个交接点。本技能只定阶段、顺序、交接点和每个环节加载哪个技能。

## 一句话

先在动手前把不确定性尽量消掉，再把执行放手给代理，再用固定节拍从顶层回看。人的注意力只花在定义边界和高层判断上。

## 适用范围

这条流是为大改动设计的，先判断够不够格，不够格就不走。

| 走这条流 | 不走这条流 |
| --- | --- |
| 复杂系统新增一个领域 | 小的缺陷修复 |
| 跨多个领域的功能纵线交付 | 快速原型，验证一个想法 |
| 子系统重构 | 小规模的增量接口设计与实现 |
| 较大规模的改造 | 一处局部修改，影响范围一眼看得清 |

判据是影响范围：改动会触及领域边界、跨域协作或系统全局的架构时才走。不走这条流的工作直接按各自的技能做，例如 `pstack:tdd`、`mattpocock-skills:prototype`、`mattpocock-skills:diagnosing-bugs`。

## 阶段与环节

| 阶段 | 环节 | 加载的技能 | 产出 |
| --- | --- | --- | --- |
| 定义期 | 1 需求与不变式 | `requirement-and-invariants` | 用户可见差异、不变式清单 |
| 定义期 | 2 领域影响与顶层设计 | `domain-impact-analysis` | 重点、次要、连带领域；总边界 |
| 定义期 | 3 技术调研与复用 | `tech-research-and-reuse` | 复用、二次开发或自造的结论 |
| 定义期 | 4 形式化守护 | `formal-guard` | 偏函数全化、数理模型、定理；转契约测试的清单 |
| 定义期 | 5 细化领域设计 | `detailed-domain-design` | 领域模型、关系模型、仓储设计 |
| 定义期 | 6 正式落盘 | `formal-docs-landing` | 三层正式文档并过评审 |
| 交接点 | 长期维护的知识已进唯一源并过评审 | 无 | 人可以把注意力移开 |
| 交付期 | 7 spec 与 plan | `spec-and-plan` | spec.md、plan.md |
| 交付期 | 8 前置消熵 | `context-pack` | 整程上下文包与关键设计；每切片的开工包：上下文增量、技术设计与验证、细化推进方案、里程碑待办清单 |
| 交付期 | 9 派发 | `delegate-brief` | 目标、边界、规格、信息包四件齐全的简报 |
| 交付期 | 10 定期回看 | `one-lesson-rule` | 后台哨兵定时唤醒的汇报；每 45 到 60 分钟的顶层回看 |
| 交付期 | 11 切片收口 | `slice-closeout` | 结构读数、差分变异、评审结论 |
| 交付期 | 12 向人汇报 | `progress-artifacts` | 可视化、可上手、用完即弃的汇报件 |
| 交付期 | 13 清理 | `cleanup` | 每切片一次中间产物清理；一程交付后一次全盘清理 |

## 规则

- 定义期的顺序不能跳：需求先于不变式，不变式先于领域，领域先于架构，架构先于实施。
- 走了这条流，定义期每一步都要有明确产出或明确的「本次不需要」结论，不能默认跳过。不够格的工作整条流都不走，而不是走个缩水版。
- 形式化守护的触发由代理建议、人确认，不自行投入。
- 交接点是物理条件，不是感觉：没进唯一源、没过评审的边界，不算定好。
- 交付期执行走 TDD，不过度设计，不过度优化。
- 主代理自己做是默认。派子代理是例外，要说出 `delegate-brief` 派发门三种理由之一。
- 计划者就是执行者：plan 由主代理写，结果回来就修订，不交给别人规划再交给别人执行。
- 一程和每个切片都带时间预算，到了预算就回看，不继续跑。
- 切片和一程的完成只认 spec 的验收标准，不认任何子代理对自己工作的报告。
- 验收与评审用确定性上下文：测试、证明、读数、变异、对照 spec 逐条核。不做对抗性评审。
- 自主推进时不过度设计、不过度优化、不陷进细节。
- 一程的汇报件统一放系统临时目录下本会话本程的子目录，不进仓库。
- 一程交付完毕的声明包含清理已做。
- 这条流只服务一个会话里的一个主代理和它的子代理，不做多会话协作。
- 各环节技能按需加载，不一次全读。
