# 单会话研发流

一程研发在一个会话里走完：人主导的定义期，代理自主的交付期，中间一个交接点。本技能只定阶段、顺序、交接点和每个环节加载哪个技能，环节的做法归各环节技能。

## 一句话

先在动手前把不确定性尽量消掉，再把执行放手给代理，再用固定节拍从顶层回看。人的注意力只花在定义边界和高层判断上。

## 写代码的四条

这四条对一切写代码的工作适用，走不走这条流都一样；主代理自己写、派子代理写都按它。出处是 ub-mode 的「先做对，再做好，守实践」，完整原则加载技能 `ub-mode`。

1. **先做对。** 先让需求要的能力正确兑现：验收标准逐条过，测试先红后绿。这一步只求对，不求漂亮，因为还不知道对的形状时，打磨的是猜测。
2. **再做好一轮。** 做对之后专门留一轮，不加新能力，只改实现：更简洁、更优雅、放到架构上正确的位置，满足 spec 写明的性能要求。两件事分开做，每一轮都短；混在一起会一边找正确一边打磨，两头都慢。
3. **不过度设计，不提前优化。** 只建当前需求要的东西，不为想象中的将来留扩展点；没有测量证明的瓶颈不优化。需要优化时不回避：spec 写了性能要求，或测量显示不满足，优化就属于「先做对」。
4. **找本质解。** 遇到问题先做结构性分析，从根源上解决，不在局部缝缝补补、兜兜转转。同一个前提下两次修补都失败，写出那个前提并推翻它；一个切片做久了，先怀疑建模（数理、形式化、领域、OOP 与 SOLID），而不是继续加代码。

## 先判断够不够格

| 走这条流 | 不走这条流 |
| --- | --- |
| 复杂系统新增一个领域 | 小的缺陷修复 |
| 跨多个领域的功能纵线交付 | 快速原型，验证一个想法 |
| 子系统重构 | 小规模的增量接口设计与实现 |
| 较大规模的改造 | 一处局部修改，影响范围一眼看得清 |

判据是影响范围：改动会触及领域边界、跨域协作或系统全局的架构时才走。不够格的工作整条流都不走，不走缩水版，直接按各自的技能做：加载技能 `mattpocock-skills:tdd`、`mattpocock-skills:prototype` 或 `mattpocock-skills:diagnosing-bugs`。人问的是这条流怎么用、自己该做什么，不是要开工，加载技能 `teach-pqw-skills`。

## 开工动作

1. 第一条回复先用自己的话复述人的目标、要解决的问题、预计的影响范围，不等确认。加载技能 `pstack:in-your-own-words`。证据排除了人要的改动时，给出证据并停下。
2. 把下表的 13 个环节按顺序写进会话的任务清单，排在任何任务专有待办之前。宿主有任务清单工具就用它；没有就在项目 tmp 下本程目录写 `todo.md`。不做的环节留在清单里，写「跳过：<理由>」，不删。
3. 会话中途人说「新任务」或提出另一个需求，重新从够不够格判起。

## 阶段与环节

| 阶段 | 环节 | 加载的技能 | 产出 |
| --- | --- | --- | --- |
| 定义期 | 1 需求与不变式 | `requirement-and-invariants` | 需求与不变式单：用户可见差异、不变式清单 |
| 定义期 | 2 领域影响与顶层设计 | `domain-impact-analysis` | 领域影响分级表：重点、次要、连带领域；总边界 |
| 定义期 | 3 技术调研与复用 | `tech-research-and-reuse` | 复用论证单：直接复用、二次开发、二次封装或自造 |
| 定义期 | 4 形式化守护 | `formal-guard` | 形式化触发建议单；偏函数全化、模型与证明；转契约测试的清单 |
| 定义期 | 5 细化领域设计 | `detailed-domain-design` | 细化设计清单：领域模型、关系模型、仓储设计 |
| 定义期 | 6 正式落盘 | `formal-docs-landing` | 落盘决定表；三层正式文档并过评审 |
| 交接点 | 长期维护的知识已进唯一源并过评审 | [交接点核对单](handoff-checklist.md) | 人可以把注意力移开 |
| 交付期 | 7 spec 与 plan | `spec-and-plan` | spec.md、plan.md |
| 交付期 | 8 前置消熵 | `context-pack` | 整程上下文包与关键设计；每切片的开工包：上下文增量、技术设计与验证、细化推进方案、里程碑待办清单 |
| 交付期 | 9 派发 | `delegate-brief` | 过派发门；目标、边界、规格、信息包四件齐全的简报 |
| 交付期 | 10 定期回看 | `one-lesson-rule` | 哨兵定时唤醒的汇报；每 45 到 60 分钟的顶层回看记录 |
| 交付期 | 11 切片收口 | `slice-closeout` | 收口清单：类型检查与 lint、对照 spec、结构读数、差分变异、去 slop、证明可用 |
| 交付期 | 12 向人汇报 | `progress-artifacts` | 可视化、可上手、用完即弃的汇报件 |
| 交付期 | 13 清理 | `cleanup` | 每切片一次中间产物清理；一程交付后一次全盘清理与交付声明 |

## 怎样走

1. 定义期 1 到 6 顺序走，每步加载对应技能，产出填该技能的模板。人在场，代理不替人认可。
2. 到交接点走一遍核对单。过了，人可以离开。
3. 交付期先 7，再 8 的整程包，然后按 plan 的切片循环：切片开工包（8）、做对（TDD，验收标准逐条过）、做好一轮（不加能力，只改实现）、收口（11）、汇报（12）、切片清理（13）。做对与做好一轮的分法见上一节[写代码的四条](#写代码的四条)。10 从第一个切片开工起常驻。9 只在派子代理时加载。
4. 全部切片完成后做一程清理与交付声明（13），出最后一份汇报件（12）。

实施本身：方法加载技能 `mattpocock-skills:tdd`；执行风格加载技能 `pstack:poteto-mode`。

## 不可商量的

**顺序。** 需求先于不变式，不变式先于领域，领域先于架构，架构先于实施。走了这条流，定义期每一步都要有明确产出或明确的「本次不需要」结论，不能默认跳过。形式化守护的触发由代理建议、人确认，不自行投入。

**交接。** 交接点是物理条件，不是感觉：没进唯一源、没过评审的边界，不算定好。

**验收。** 切片和一程的完成只认 spec 的验收标准，不认任何子代理对自己工作的报告。验收与评审用确定性上下文：测试、证明、读数、变异、对照 spec 逐条核。不做对抗性评审。

**派发。** 主代理自己做是默认。派子代理是例外，要说出 `delegate-brief` 派发门三种理由之一。计划者就是执行者：plan 由主代理写，结果回来就修订，不交给别人规划再交给别人执行。

**自主。** 一程和每个切片都带时间预算，到了预算就回看，不继续跑。自主推进时按[写代码的四条](#写代码的四条)，不陷进细节。

**边界。** 这条流只服务一个会话里的一个主代理和它的子代理，不做多会话协作。汇报件统一放系统临时目录下本会话本程的子目录，不进仓库；一程交付完毕的声明包含清理已做。各环节技能按需加载，不一次全读。项目的命令与位置从消费者 AGENTS.md 的「pqw-skills 接入」一节取；没填的槽位按「未提供」处理，不猜。

## 容易混的环节

- `spec-and-plan` 写目标、边界与切片；`context-pack` 写动手前要知道的事。先有 plan，再做整程包与开工包。
- `one-lesson-rule` 是节拍，`progress-artifacts` 是内容。哨兵醒了先回看，回看有结论才出汇报件。
- `slice-closeout` 核承诺有没有做到；`delegate-brief` 的验收防作弊只管子代理交回的东西怎么核，不替代收口。
- `cleanup` 切片级只清中间产物；一程级连汇报件一起清，并出交付声明。
- `formal-guard` 是代理建议、人确认的守护；`tech-research-and-reuse` 的调研不替代它。
